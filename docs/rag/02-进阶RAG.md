# 阶段二：进阶 RAG（Advanced RAG）

> 进阶 RAG 不推翻基础管道，而是围绕「**检索前（Pre-Retrieval）→ 检索中（During-Retrieval）→ 检索后（Post-Retrieval）**」三个环节做精细化优化，直接对症下药解决基础 RAG 的六大痛点。这是生产级 RAG 的「主力军」。

## 一、优化总览：三个环节

```
用户问题
   │
   ├─[检索前] 查询改写 / 扩展 / HyDE / 子问题拆解
   │         ↓ 得到"更易检索"的查询
   ├─[检索中] 混合检索(稀疏+稠密) / 语义分块 / 元数据过滤 / 多路召回
   │         ↓ 得到候选 chunk（Top-N，N 较大）
   ├─[检索后] 重排序(Rerank) / 上下文压缩 / 去重
   │         ↓ 得到精炼 Top-K（K 较小）
   └─[生成]  拼接 → LLM
```

核心思想：**检索前让"问题更会问"，检索中让"召回更全面"，检索后让"喂给模型的内容更干净"。**

## 二、检索前优化（Pre-Retrieval）

目标：解决「用户问题表述差、与文档用词不一致」导致的检索失败。

### 2.1 查询改写（Query Rewriting）

- **问题**：用户口语化提问（"那个退款咋弄"）与文档书面语（"退款流程说明"）用词不匹配，向量检索相似度低。
- **做法**：用 LLM 把原始问题改写为更规范、更贴近文档语料的检索查询。
- **示例**：
  - 原问题：*“这玩意儿咋连不上网”*
  - 改写后：*“设备无法连接 Wi-Fi 网络的故障排查步骤”*
- **价值**：低成本、高性价比，通常是进阶 RAG 第一个要加的优化。

### 2.2 查询扩展 / 多查询（Multi-Query）

- **做法**：让 LLM 从一个问题生成多个不同角度/表述的查询（如 3~5 个），分别检索后合并结果。
- **收益**：覆盖不同用词与侧面，提升召回率（避免单一表述漏检）。
- **注意**：需对多路结果做**去重 + 重排**，否则噪声会叠加。

### 2.3 RAG-Fusion（融合检索）

- **做法**：Multi-Query 的进阶版。对每路查询检索得到排名，用 **Reciprocal Rank Fusion（RRF，倒数排名融合）** 把多路结果融合成一个综合排序：
  ```
  RRF_score(d) = Σ  1 / (k + rank_i(d))      k 通常取 60
              i
  ```
- **价值**：比简单合并更稳健，能突出"多路都命中"的高质量文档。

### 2.4 HyDE（Hypothetical Document Embeddings）

- **思想**：先让 LLM 针对问题**生成一段"假设性答案"**，再用这段假答案的 embedding 去检索（而非用问题本身）。
- **原理**：假答案的用词/语义更接近真实文档，与知识库向量更匹配，召回更准。
- **代价**：多一次 LLM 生成调用（延迟/成本上升）；假答案可能引入偏差。
- **适用**：问题抽象、文档表述与问题差异大时效果好。

### 2.5 子问题分解（Sub-Question Decomposition）

- **做法**：对复杂/多跳问题，用 LLM 拆成若干子问题，逐个子问题检索，再汇总。
- **代表**：LlamaIndex 的 `SubQuestionQueryEngine`。
- **适用**：需要跨文档、多事实拼装的复杂问答。

### 2.6 退一步提问（Step-Back Prompting）

- **做法**：先让模型提出一个更宏观/更抽象的"背景性问题"并检索，再回答原问题。
- **价值**：对需要高层概念支撑的问题有帮助（详见模块化/智能体阶段）。

## 三、检索中优化（During-Retrieval）

目标：让召回既"广"（不漏）又"准"（不噪），并改善分块质量。

### 3.1 混合检索（Hybrid Search）= 稀疏 + 稠密

这是进阶 RAG **最核心**的优化之一。

| 检索类型 | 代表 | 原理 | 擅长 |
| --- | --- | --- | --- |
| **稀疏检索（Sparse）** | BM25、TF-IDF | 关键词精确匹配、词频统计 | 专有名词、ID、精确术语、罕见词 |
| **稠密检索（Dense）** | Embedding 向量 | 语义相似度 | 同义改写、语义相近但用词不同 |

- **混合方式**：分别检索后融合（RRF 或加权求和），兼顾"关键词命中"与"语义匹配"。
- **结论**：几乎所有生产级 RAG 都建议上混合检索，因为它同时解决"语义召回"和"精确词召回"两类失败。

### 3.2 分块策略升级

| 策略 | 说明 | 解决什么痛点 |
| --- | --- | --- |
| **语义分块（Semantic Chunking）** | 用 embedding 相似度下降处作为边界切分 | 避免硬切割裂语义（基础 RAG 痛点②） |
| **父子分块（Parent-Child / Small-to-Big）** | 小块（child）用于精准检索，命中后返回其大块父文档（parent）给 LLM | 兼顾"检索精度"与"上下文完整" |
| **滑动窗口（Sliding Window）** | 块之间保留重叠（overlap），或用扩大窗口 | 缓解边界信息丢失 |
| **命题式分块（Proposition Chunking）** | 把文本拆成独立命题（原子事实）再嵌入 | 粒度极细、噪声低 |

> **父子分块**极其常用：检索时用小块保证准确度，生成时给大模型看大块保完整，一举两得。

### 3.3 元数据过滤（Metadata Filtering）

- **做法**：检索前先用元数据缩小范围（如时间范围、文档类型、部门、标签）。
- **示例**：`过滤 "部门=法务" 且 "时间>2024"` 后再做向量检索。
- **价值**：大幅降噪、提效，尤其适合企业多源知识库。
- **实现**：向量库普遍支持元数据过滤（Milvus/Qdrant/Weaviate/pgvector 等）。

### 3.4 多路召回（Multi-Index / Multi-Source）

- 不同来源/语言/模态走不同索引，分别召回后融合。
- 适合知识库异构（技术文档 + 客服录音转写 + 数据库）。

## 四、检索后优化（Post-Retrieval）

目标：在把 chunk 喂给 LLM **之前**，进一步精炼、排序、压缩，解决"噪声多、冗余、超窗口"。

### 4.1 重排序（Reranking）—— 进阶 RAG 的另一核心

- **为何需要**：向量检索（Bi-Encoder，查询与文档独立编码）速度快但精度有限；它只能做"粗排"拿到 Top-N（如 20~50）。
- **做法**：把「问题 + 每个候选 chunk」成对地送入 **Cross-Encoder 重排模型**，模型同时看两边、输出相关性分数，再重新排序取 Top-K（如 3~5）。
- **代表模型**：BGE-Reranker、Cohere Rerank、Jina Reranker、RankGPT（用 LLM 排序）。
- **典型管线**：`向量召回 Top-50 → 重排 → 取 Top-5 给 LLM`。
- **收益**：准确率显著提升，被认为是"性价比最高"的优化之一。
- **代价**：Cross-Encoder 需逐对计算，比向量检索慢，故只用于少量候选（先召回后重排）。

```
召回 Top-50（快但粗） ──► 重排模型 ──► Top-5（准） ──► LLM
```

### 4.2 上下文压缩（Context Compression）

- **问题**：检索到的 chunk 往往很长，但真正有用的只是其中一两句，塞满上下文既费 token 又稀释注意力。
- **做法**：
  - **抽取式压缩**：用 LLM/小模型从 chunk 中抽取与问题相关的句子。
  - **摘要式压缩**：把 chunk 压缩为关键句摘要（如 LangChain `ContextualCompressionRetriever`）。
- **价值**：省 token、提信噪比、缓解长上下文注意力分散。

### 4.3 去重与冲突检测

- 多路召回结果可能重复或彼此矛盾。
- 简单做法：按来源/内容相似度去重；进阶做法：让 LLM 检测冲突并标注。

## 五、进阶 RAG 典型组合与收益

一个「够用且高效」的进阶 RAG 生产基线推荐：

```
查询改写 + 混合检索(BM25+向量) + 父子分块 + 元数据过滤
        → 召回 Top-30 → 重排序 → Top-5 → 上下文压缩 → LLM
```

| 优化项 | 投入 | 典型收益 |
| --- | --- | --- |
| 查询改写 | 低（1 次 LLM） | 召回率↑，尤其口语化问题 |
| 混合检索 | 中（双索引） | 精确词+语义双覆盖 |
| 重排序 | 中（Rerank 模型） | 准确率↑↑，性价比最高 |
| 父子分块 | 低 | 检索精度+上下文完整兼得 |
| 上下文压缩 | 中 | 降噪、省 token |

> 经验法则：**先上加「查询改写 + 混合检索 + 重排序」三件套**，通常就能把基础 RAG 的准确率拉到一个可接受的区间。

## 六、常见坑与调试清单

1. **只调生成不调检索**：准确率问题 80% 出在检索。先验证「检索到的 chunk 是否真的包含答案」。
2. **Top-K 盲目调大**：噪声随之上升，应配合重排使用。
3. **Embedding 模型与检索域不匹配**：通用 embedding 在垂直领域（医疗/法律）表现差，必要时用领域数据微调 embedding。
4. **重排模型与生成模型语言不一致**：中文场景请用中文重排模型（如 BGE-Reranker-v2-m3）。
5. **忽视元数据**：有时间/类别字段却不用过滤，白白引入噪声。
6. **缺少评测闭环**：优化前后必须用评测集（见 [05-前沿与趋势.md](./05-前沿与趋势.md) 的 RAGAS）量化对比。
